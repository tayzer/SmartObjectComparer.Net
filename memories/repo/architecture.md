- Hosts (`Cli`, `Web`, `Desktop`) are thin composition roots. All three enter at `RequestComparisonWorkflowService` and share one DI root: `Source/ParityBench.NET.Composition/WorkspaceServiceCollectionExtensions.cs` (`AddParityBenchWorkspaceServices`, plus `AddParityBenchUiServices` for Web/Desktop). No host owns comparison logic.
- `ComparisonRunExecutor` runs two bounded worker pools joined by a `System.Threading.Channels` channel: execution persists each response artifact as it lands, comparison reopens and diffs persisted artifacts. Run memory is bounded rather than proportional to run size.
- Client behaviour lives in plugins: versioned packages compiled only against `ParityBench.PluginSdk`, discovered at run time from `plugins/`, loaded into a collectible `AssemblyLoadContext`, and selected by a saved run profile under `<workspace>/config/profiles/`. Profiles reference stable logical ids only, never .NET type names.
- `UseWorkerProcessExecution` (opt-in, `Worker:Enabled=true`) swaps the in-process executor for `WorkerComparisonRunExecutor`, running the same path inside `ParityBench.NET.Worker` and relaying progress and results over a named pipe.
- The legacy compile-time `IContractProfile` / preset / response-model-registry path still exists and still backs raw structured comparison and fixtures. It is superseded, not removed.
- `RunOptions.Baseline` selects capture or replay. Replay reads the stored canonical comparison model straight into the slot, skipping `Input`–`Mapping` entirely, so the captured version is never called. Baselines require a plugin comparison.
